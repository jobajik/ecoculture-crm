# Настройка и запуск Ecoculture-CRM — пошаговая инструкция

Инструкция рассчитана на человека без опыта в Google Cloud — просто идите по шагам по порядку.
На всё уйдёт примерно 40–60 минут.

## Что понадобится

- Google-аккаунт компании (лучше корпоративный, не личный) — на нём будет создан проект в Google Cloud.
- Аккаунт на GitHub (бесплатно) — там будет храниться код.
- Аккаунт на [Vercel](https://vercel.com) (бесплатно, регистрация через GitHub) — это и есть хостинг,
  за который вы платите (есть бесплатный тариф Hobby, платный Pro — от $20/мес, если понадобится
  свой домен для нескольких проектов или больше ресурсов).

---

## Шаг 1. Создать проект в Google Cloud

1. Откройте [console.cloud.google.com](https://console.cloud.google.com/) и войдите под тем
   Google-аккаунтом, от имени которого будет жить система.
2. Вверху рядом с логотипом Google Cloud нажмите на выпадающий список проектов → **New Project**.
3. Назовите проект, например `flower-crm`, и нажмите **Create**.
4. Убедитесь, что этот проект выбран (виден в шапке).

## Шаг 2. Включить Google Sheets API

1. В поиске вверху введите **Google Sheets API** → откройте найденную страницу → **Enable**.

## Шаг 3. Настроить экран согласия (OAuth consent screen)

Это экран, который сотрудники увидят при первом входе через Google.

1. Слева в меню: **APIs & Services → OAuth consent screen**.
2. User Type: если у компании есть Google Workspace (корпоративная почта на своём домене) — выберите
   **Internal** (тогда войти смогут только сотрудники с почтой вашего домена, это удобнее и безопаснее).
   Если сотрудники используют обычные gmail.com — выберите **External**.
3. Заполните название приложения («Ecoculture-CRM»), почту поддержки, почту разработчика — можно вашу.
4. На шаге Scopes ничего добавлять не нужно (используются только базовые: email, profile).
5. Если выбрали **External** — на шаге **Test users** добавьте email всех сотрудников, которые будут
   входить в систему, пока приложение не прошло верификацию Google (для внутреннего инструмента
   верификация не нужна — просто держите всех сотрудников в списке Test users, лимит 100 адресов).
6. Сохраните.

## Шаг 4. Создать OAuth Client ID (для входа менеджеров и зав.складом)

1. **APIs & Services → Credentials → + Create Credentials → OAuth client ID**.
2. Application type: **Web application**. Имя: например «Ecoculture-CRM Web».
3. **Authorized redirect URIs** — добавьте сразу два адреса (второй понадобится после деплоя, но можно
   добавить домен заранее, а поправить позже, если он изменится):
   - `http://localhost:3000/api/auth/callback/google` — для локальной разработки
   - `https://ВАШ-ДОМЕН/api/auth/callback/google` — для сайта в проде (домен узнаете на шаге 10;
     сюда же можно добавить и временный адрес вида `https://flower-crm.vercel.app/api/auth/callback/google`)
4. Нажмите **Create**. Появятся **Client ID** и **Client Secret** — скопируйте оба, они понадобятся
   в `.env.local`.

## Шаг 5. Создать сервисный аккаунт (доступ к Google-таблице)

Сервисный аккаунт — это «робот-пользователь», от имени которого сайт читает и пишет в таблицу.

1. **APIs & Services → Credentials → + Create Credentials → Service account**.
2. Имя, например `flower-crm-sheets`. Роль можно не назначать (доступ будет дан прямо на уровне
   таблицы на шаге 6) — нажмите **Done**.
3. Откройте созданный сервисный аккаунт → вкладка **Keys → Add Key → Create new key → JSON**.
   Скачается `.json`-файл — **храните его в секрете**, в нём приватный ключ.
4. Внутри файла найдите поля `client_email` и `private_key` — они понадобятся для `.env.local`.

> **Если появилась ошибка «Service account key creation is disabled»** — у вашей организации в
> Google Cloud политикой запрещено создавать ключи сервисных аккаунтов, и это не всегда получается
> снять через интерфейс (IAM & Admin → Organization Policies → `iam.disableServiceAccountKeyCreation`
> → override для проекта; если опция недоступна — политикой управляет кто-то другой). В этом случае
> **пропустите шаг 5 целиком** и используйте **Вариант Б** ниже — он не требует сервисного аккаунта
> вообще.

### Вариант Б — без сервисного аккаунта (если шаг 5 недоступен)

Вместо робота-аккаунта сайт будет заходить в таблицу от имени вашего обычного Google-аккаунта —
через тот же вход, что уже настроен на шаге 4. Организационная политика запрещает только ключи
сервисных аккаунтов, а не обычную авторизацию человека, так что это надёжно работает в обход
блокировки.

1. Убедитесь, что в `.env.local` уже заполнены `GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET` (шаг 4).
2. В Google Cloud Console: **Credentials → тот же OAuth client → Authorized redirect URIs** →
   добавьте ещё один адрес: `http://localhost:4321/oauth2callback`.
3. В папке проекта выполните `npm install`, если ещё не делали, затем:
   ```
   npm run get-refresh-token
   ```
4. Скрипт напечатает ссылку — откройте её в браузере и войдите тем Google-аккаунтом, которому будет
   принадлежать таблица (см. шаг 6). Если Google покажет предупреждение «приложение не проверено» —
   это ожидаемо для собственного инструмента: нажмите «Дополнительные настройки» → «Перейти на
   flower-crm (небезопасно)» → «Продолжить».
5. После разрешения доступа в терминале появится строка вида
   `GOOGLE_OAUTH_REFRESH_TOKEN=1//0g...` — скопируйте её целиком в `.env.local` **вместо**
   `GOOGLE_SERVICE_ACCOUNT_EMAIL` и `GOOGLE_SERVICE_ACCOUNT_PRIVATE_KEY` (эти два поля тогда оставьте
   пустыми).

Дальше следуйте шагам как обычно — просто там, где встречается «сервисный аккаунт», для вас это
неактуально: таблица работает от вашего собственного аккаунта.

## Шаг 6. Создать Google-таблицу

1. Создайте новую таблицу на [sheets.google.com](https://sheets.google.com) (можно из-под того же
   аккаунта или из общего диска компании), назовите её, например, «Ecoculture-CRM — данные».
2. Скопируйте её ID — это часть ссылки между `/d/` и `/edit`:
   `https://docs.google.com/spreadsheets/d/ЭТО_ID/edit`
3. **Если используете Способ А (сервисный аккаунт):** нажмите **Настройки доступа (Share)** →
   добавьте email сервисного аккаунта из шага 5 (`...@...gserviceaccount.com`) с ролью **Редактор**.
   Без этого приложение не сможет писать в таблицу.
   **Если используете Вариант Б:** ничего расшаривать не нужно — просто создайте таблицу тем же
   Google-аккаунтом, которым будете авторизовываться в `npm run get-refresh-token` (или дайте этому
   аккаунту доступ редактора, если таблицу создал кто-то другой).

## Шаг 7. Настроить переменные окружения и создать вкладки

1. Скопируйте `.env.example` в `.env.local` и заполните (нужен ровно один блок — А или Б):

```
GOOGLE_CLIENT_ID=...              # из шага 4
GOOGLE_CLIENT_SECRET=...          # из шага 4
NEXTAUTH_SECRET=...               # сгенерировать: openssl rand -base64 32
NEXTAUTH_URL=http://localhost:3000

GOOGLE_SHEETS_SPREADSHEET_ID=...  # из шага 6

# Способ А (сервисный аккаунт):
GOOGLE_SERVICE_ACCOUNT_EMAIL=...  # client_email из JSON-файла шага 5
GOOGLE_SERVICE_ACCOUNT_PRIVATE_KEY=...  # private_key из JSON-файла, см. ниже

# — или Способ Б (если Google блокирует ключи, см. "Вариант Б" в шаге 5):
GOOGLE_OAUTH_REFRESH_TOKEN=...    # печатает npm run get-refresh-token
```

   Приватный ключ в JSON-файле выглядит так:
   ```
   "-----BEGIN PRIVATE KEY-----\nMIIEvQ...много строк...\n-----END PRIVATE KEY-----\n"
   ```
   Скопируйте это значение **целиком, вместе с кавычками не нужно, но `\n` оставьте как есть** —
   вставьте одной строкой в `.env.local`:
   ```
   GOOGLE_SERVICE_ACCOUNT_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----\nMIIEvQ...\n-----END PRIVATE KEY-----\n"
   ```

2. Установите зависимости и создайте вкладки в таблице автоматически:

```bash
npm install
npm run setup-sheet
```

Скрипт создаст вкладки `Users`, `Orders`, `OrderItems`, `Batches`, `Shipments`, `Writeoffs`,
`PriceHistory`, `Settings` с нужными заголовками и заполнит `Settings` значениями по умолчанию
(срок хранения розы — 7 дней, хризантемы — 18 дней; можно поменять прямо в таблице).

## Шаг 8. Добавить сотрудников

Откройте вкладку **Users** в таблице и добавьте по одной строке на каждого сотрудника:

| Email | Name | Role | Active | Farm |
|---|---|---|---|---|
| ivan@company.kz | Иван Петров | manager | TRUE |  |
| aigerim@company.kz | Айгерим С. | warehouse | TRUE | rose_farm |
| serik@company.kz | Серик К. | warehouse | TRUE | esentai |
| you@company.kz | Вы | admin | TRUE |  |

Роли: `manager` (принимает заявки), `warehouse` (зав. складом, отгружает/принимает партии),
`accountant` (бухгалтер: отмечает оплаты, ведёт долги, выгружает отчёт), `admin` (видит и делает
всё, плюс раздел «Настройки»). Без строки в этой вкладке человек не сможет войти, даже если у него
есть Google-аккаунт — это и есть контроль доступа.

### Бухгалтер и две зелёные галочки

Строка бухгалтера выглядит так — колонка `Farm` у неё пустая, она работает по обоим производствам:

| Email | Name | Role | Active | Farm |
|---|---|---|---|---|
| buh@company.kz | Имя | `accountant` | TRUE |  |

Заявка попадает на сборку, когда на ней стоят **две галочки**:

1. **Менеджер подтвердил** — ставит менеджер на странице своей заявки, когда окончательно
   договорился с клиентом;
2. **Оплачено** — ставит бухгалтер в разделе «Оплаты», когда увидела деньги.

В листе сборки такие заявки помечены зелёным `✓✓`, а неготовые — красным `✗`. Неоплаченные из листа
**не исчезают**: зав. складом их видит и решает сама, чтобы срочный заказ не потерялся из-за того,
что бухгалтер не успела отметить оплату.

Оплата отмечается целиком: частичных оплат и предоплат в системе нет. Способ оплаты — «Каспи» или
«Наличные».

### Планы и бонусы менеджеров

Планы задаются на вкладке **Plans**: `Period` (месяц в виде `2026-09`), `ManagerEmail`,
`TargetAmount`, `TargetStems`.

Бонус считается автоматически и зависит от цветка:

| Цветок | Производство | Бонус |
|---|---|---|
| Роза, эустома | Rose Farm | **1,5%** от проданного |
| Хризантема | Есентай Агро Хим | **2%** от проданного |

Бонус начисляется **только с оплаченных заявок** — пока бухгалтер не отметила деньги, бонуса нет.
Неоплаченное показывается отдельно как «бонус ждёт». В разделе «Продажи» → «Рейтинг и бонусы»
менеджеры видят и свои результаты, и результаты коллег.

### Колонка Farm — два производства

В компании два ТОО, и у каждого свой зав. складом:

| Код для колонки Farm | Производство | Что выращивает |
|---|---|---|
| `rose_farm` | Rose Farm | розы, эустома |
| `esentai` | Есентай Агро Хим | хризантема |

Колонка `Farm` заполняется **только для роли `warehouse`**. Такой зав. складом:

- видит на складе и в остатках только цветок своего производства;
- принимает партии (вручную и Excel-файлом) и списывает только свой цветок — чужой система
  не примет и покажет понятную ошибку;
- отгружает только свои позиции;
- печатает сводную заявку на день по своему производству (в шапке документа стоит название ТОО),
  а Excel-шаблон приёмки скачивается уже с его культурами и сортами.

Менеджеры и `admin` работают по обоим производствам: менеджер оформляет заявку с любым цветком,
а на печать она автоматически разделяется — каждому зав. складом уходит своя часть. В аналитике
(«Продажи» и «Продажи за день») продажи дополнительно разложены по производствам.

Если вы обновляете уже работающую CRM, где колонки `Farm` ещё не было — запустите
`npm run setup-sheet` ещё раз: он допишет заголовок `Farm` в конец строки заголовков вкладки
`Users`. Уже заполненные строки при этом не сдвигаются — у них колонка `Farm` просто останется
пустой. После этого проставьте коды производств зав. складом (`rose_farm` / `esentai`) и попросите
их заново войти в систему — роль и производство подхватываются при входе.

## Шаг 9. Запустить локально и проверить

```bash
npm run dev
```

Откройте `http://localhost:3000`, нажмите «Войти через Google», используйте почту, которую добавили
на вкладку Users. Проверьте: создать заявку менеджером, принять партию и отгрузить складом,
открыть «Аналитику».

## Шаг 10. Деплой на хостинг (Vercel)

1. Загрузите код в GitHub (создайте пустой репозиторий на github.com и запушьте в него содержимое
   этой папки — `git init`, `git add .`, `git commit -m "init"`, затем следуйте инструкции GitHub
   «…or push an existing repository»).
2. Зайдите на [vercel.com](https://vercel.com), войдите через GitHub, нажмите **Add New → Project**,
   выберите ваш репозиторий.
3. Framework Preset определится автоматически как **Next.js** — ничего менять не нужно.
4. В разделе **Environment Variables** добавьте те же переменные, что в `.env.local`:
   `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `NEXTAUTH_SECRET`, `NEXTAUTH_URL` (сюда впишите
   финальный адрес сайта, например `https://flower-crm.vercel.app`, поправите на свой домен позже),
   `GOOGLE_SHEETS_SPREADSHEET_ID`, и в зависимости от того, каким способом вы подключали таблицу в
   шаге 5/7 — либо `GOOGLE_SERVICE_ACCOUNT_EMAIL` + `GOOGLE_SERVICE_ACCOUNT_PRIVATE_KEY` (Способ А),
   либо только `GOOGLE_OAUTH_REFRESH_TOKEN` (Способ Б).
5. Нажмите **Deploy**. Через 1–2 минуты сайт будет доступен по адресу вида
   `https://flower-crm-xxxx.vercel.app`.
6. Вернитесь в Google Cloud (шаг 4) и добавьте в **Authorized redirect URIs** точный адрес:
   `https://ВАШ-АДРЕС/api/auth/callback/google`.
7. Если хотите свой домен (например, `crm.вашакомпания.kz`): в Vercel откройте проект → **Settings →
   Domains**, добавьте домен и настройте у себя в DNS записи, которые покажет Vercel. После этого
   обновите `NEXTAUTH_URL` в переменных окружения на новый домен и добавьте его же в Authorized
   redirect URIs в Google Cloud.

Готово — сайт работает, и вы сами управляете хостингом и оплатой.

## Планы продаж по менеджерам

На вкладке **Plans** задаются месячные планы — по строке на менеджера:

| Period | ManagerEmail | TargetAmount | TargetStems |
|---|---|---|---|
| 2026-09 | ivan@company.kz | 4500000 | 120000 |
| 2026-09 | aigerim@company.kz | 3000000 | 80000 |

`Period` — месяц в формате ГГГГ-ММ. План компании считается как сумма планов менеджеров, отдельной
строки для него не нужно. Раздел «Продажи» в CRM показывает факт против этих цифр: за сегодня, за
месяц, процент выполнения, прогноз по текущему темпу и сколько нужно продавать в день, чтобы выйти
на план. Планы на новый месяц просто дописываются новыми строками.

## Настройка сроков хранения

На вкладке **Settings** таблицы:

- `ShelfLifeDays_rose` — сколько суток хранится роза, пока не станет критично (по умолчанию 7).
- `ShelfLifeDays_chrysanthemum` — то же для хризантемы (по умолчанию 18).
- `WarningThresholdPercent` — при какой доле от этого срока партия помечается жёлтым
  «требует внимания» (по умолчанию 70, то есть после 70% срока).

Изменения применяются сразу, без перезапуска сайта.

## Как это устроено и какие есть ограничения

- **Google Таблица как база данных.** Это осознанный выбор для небольшой/средней компании: не нужно
  администрировать отдельную БД, всё видно и можно поправить руками. Ограничения: у Google Sheets API
  есть лимиты (по умолчанию около 300 запросов в минуту на проект, 60 — на одного пользователя) —
  для одной компании с несколькими сотрудниками этого достаточно с большим запасом; настоящих
  транзакций нет, поэтому при одновременном редактировании одной и той же партии двумя людьми
  в один и тот же момент возможна редкая рассинхронизация — она видна в таблице и легко правится
  вручную.
- **Роли и доступ** полностью управляются вкладкой `Users` — без правок кода.
- **FIFO по сроку хранения**: при отгрузке склад видит партии одного сорта, отсортированные по дате
  сбора — предлагается сначала отгружать то, что лежит дольше.

## Устранение типичных неполадок

- **`redirect_uri_mismatch` при входе** — адрес в браузере не совпадает ни с одним из Authorized
  redirect URIs в Google Cloud (шаг 4). Добавьте точный адрес (с `https://`, без слэша на конце,
  с `/api/auth/callback/google`).
- **«Ваш Google-аккаунт не найден среди сотрудников»** — email отсутствует на вкладке `Users` или
  `Active` не `TRUE`. Добавьте/поправьте строку.
- **`PERMISSION_DENIED` / 403 при обращении к таблице** — сервисный аккаунт не добавлен как
  редактор в саму таблицу (шаг 6, пункт 3), либо не совпадает `GOOGLE_SHEETS_SPREADSHEET_ID`.
- **Ошибка про приватный ключ (`error:0909006C` / `DECODER routines`)** — при копировании ключа в
  `.env.local` потерялись переносы строк `\n` или кавычки. Скопируйте значение `private_key` из
  JSON-файла заново, целиком.
- **`"npm" не является внутренней или внешней командой`** (Windows) или `command not found: npm`
  (Mac) — на компьютере не установлен Node.js. Скачайте LTS-версию с [nodejs.org](https://nodejs.org),
  установите как обычную программу, затем **закройте и заново откройте окно терминала** (уже открытое
  окно не увидит свежую установку) и повторите команды.
- **`npm run get-refresh-token` не открывает нужную страницу / зависает** — проверьте, что адрес
  `http://localhost:4321/oauth2callback` добавлен в Authorized redirect URIs того же OAuth client,
  что и `GOOGLE_CLIENT_ID` в `.env.local` (см. "Вариант Б" в шаге 5).
